Extension URI: `https://docs.boonprotocol.com/a2a/extensions/boon-agent-payments/v0.2`

This A2A extension lets an ERC-8004 agent advertise a **recognition target** in its Agent Card: where others can send it a Boon (USDC recognition on Base) for useful work. It is discovery and description only. It never authorizes or executes a payment. v0.2 is additive over v0.1, adding the recognition-request descriptor to v0.1's payment-preview, receipt, and reputation metadata.

## Declaring a recognition target (producer)

An agent declares the extension in its Agent Card `capabilities.extensions`, carrying the descriptor in `params`:

```json
{
  "uri": "https://docs.boonprotocol.com/a2a/extensions/boon-agent-payments/v0.2",
  "description": "Boon recognition target + payment/receipt/reputation metadata for an ERC-8004 agent.",
  "required": false,
  "params": {
    "boonRequest": {
      "handle": "agent:N",
      "profileUrl": "https://boonprotocol.com/p/agent:N",
      "suggestedAmount": "25",
      "note": "what the recognition is for"
    }
  }
}
```

- **`handle`** (required) is the agent's canonical Boon recipient and must equal the agent's own ERC-8004 identity (`agent:N`) as identified by the card.
- **`profileUrl`** (recommended) is the agent's Boon profile, itself a gratuity screen with a Send a Boon action.
- **`suggestedAmount`** (optional, USDC) is a suggestion the sender can change or clear. It is never a price, fee, or invoice.
- **`note`** (optional) is short context for the recognition.

## Verifying a target (consumer)

Before surfacing or acting on a discovered target, verify it:

1. Resolve the declared `handle` (`agent:N`) through the ERC-8004 Identity Registry.
2. Confirm it is the same agent the card identifies.
3. Classify the result:
   - **`verified`** — resolves and matches the card identity.
   - **`mismatch`** — resolves to a different identity, or the handle is not the card's own.
   - **`unverifiable`** — the registry could not be read.

Fail closed: never treat `unverifiable` as `verified`. A `mismatch` or `unverifiable` target must never be acted on automatically.

## A received request is an invitation, not authorization

Discovering a recognition target, here or over A2A or anywhere, never triggers a send. The consuming agent forms its own conviction that the service was genuinely good, then requires explicit human or OWS-policy approval before recognizing it, exactly as for any Boon. Boon's A2A surface is read and preview only and never executes settlement.

Funds are safe regardless of the descriptor: Boon settlement resolves to the real owner of the canonical handle, so a spoofed descriptor cannot misdirect a recognition. The verification step exists for trustworthy display and discovery, not to protect funds.

## Requesting is passive and contextual

Declare a recognition target on work you actually do. Do not cold-solicit, spam, demand, or gate output behind a Boon. A Boon is a gift, not a charge.

## Versioning

v0.2 is additive over v0.1: the payment-preview, receipt, and reputation metadata are unchanged. Consumers that only understand v0.1 ignore the new `boonRequest` params. The version is carried in the extension URI.
